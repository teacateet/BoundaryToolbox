# Local PvE death menu

In live43, the local player's visible death selection can open, confirm and close between two UI samples. A role card or deploy callback now binds the stock menu immediately; the client records the requested role before the stock confirm runs and reads the menu stack after the outermost role callback returns. When a player confirms multiple choices, the last role must match both the selected role and the actually possessed character before the client restores input. A temporary menu while waiting for birth pauses focus restoration. Repeated Esc or canceling a reopened selection does not erase the previous confirmed deployment. An unrelated menu opened after possession still keeps its focus.

A fresh menu key can arrive on the very first sample after a death. To distinguish a newly opened Leave Match prompt from a preexisting dialog, the client remembers whether the local player's recent in-game UI was clear. It still requires the native role permission and an active PvE round; a held combat key, a spectator, or a visible or foreign option layer cannot open the death menu this way. If a dialog opened before a spawn briefly leaves the stack and then reappears before the new pawn arrives, the client continues waiting without taking input away from the dialog.

The stock Cancel button can remove the Leave Match prompt and the game can then put the same widget back on the stack even though the menu is closed and gameplay is working. On the next death, the client recognizes this one case only if it recorded the player's actual Cancel on the previous deployment, observed the prompt leave the stack, and observes a fresh key opening the native menu on that same widget. It checks the displayed Leave Match text and both options again. A generic Back action, an unrelated dialog, a held key, a different player or a later death cannot use that receipt.

Cancel can also leave the local controller inactive after the new character has already spawned. In a recorded game the server still controlled that same living character, while the client had lost it for 12 seconds. The original Cancel button dispatches the prompt's Blueprint callback; the engine may run its native handler without dispatching a separate event. The split client observes either entry point, counts the click only once, and remembers the character only if it actually controlled it before the click.

If the game closes the menu and the controller loses that same living character for at least 450 ms, the client asks its own server to check possession once. A previously cancelled prompt may return to the stack: it must still be the same verified Leave dialog, with the ordinary menu and cursor closed and no new menu key. A different dialog, selection, role, death or controller invalidates the request. The client does not supply a pawn, spawn a character, change camera focus or acknowledge possession. When control instead returns naturally with a working first-person view and inputs, the client resumes observing the next death key without touching the old prompt.

The stock menu may consume the just-pressed flag before the death screen checks it. For this previously cancelled Leave prompt only, the client can also recognize a transition from released to held. It must have actually sampled the configured menu key in the same death within the previous 250 ms, and the new key state must coincide with the regular menu opening on the same confirmed Leave prompt. A held key from combat, an unavailable mapping, a stale observation or a menu that was already open does not qualify.

During redeployment the game can return that original Leave prompt a second time after it already left the selection page's stack. This can keep the role page flagged as open even after the server has accepted deployment and the client controls its living character. In this case the client waits for the original confirmation and checks that the selected and possessed roles both equal the requested role, the first-person view belongs to the living pawn, and game input is unlocked. It then asks the game's selection page to close once and leaves the background prompt alone. The confirmed role can be the previous role or a different one; an unconfirmed card click, later role mismatch, new menu, altered prompt, spectator or lost ownership cannot use this path. A subsequent death still needs its own fresh, permitted menu key. The split-client regression covers 149 cases.

In live42, closing the menu and regaining control are tracked separately. A confirmed local deployment survives a late role acknowledgement or a delayed transition into the inactive controller state. Once the player possesses their own live first-person character, the client restores game input and viewport focus; an unrelated menu keeps its focus. If the player remains dead without a pawn, the [local server component](../community-redeploy/OwnerRedeploy.hpp) checks the owner, death, selected role and active PvE round before using the game mode's normal restart. See [live42 verification](../../../docs/BRT-LIVE42.md).

In the split client used for live39, clicking a visible, enabled role card selects that card even if the pointer never hovered over it. Both the card and the deploy button use the current local match's role list. The stock deploy callback receives the selected role, then the stock controller takes game input back after selection. A restart request from an inactive controller still goes through the server's normal spawn checks. See [live39 verification](../../../docs/BRT-LIVE39.md).

Both community clients can open the original role selection screen when a dead local player presses their configured in-game menu action and the game presents its Leave Match confirmation. The original widget handles Back first. Role selection opens once its prompt has left the stack and the controller still permits role selection.

If no prompt appears, the same local death action now opens role selection after the observed press and release on an otherwise empty screen. A player who releases during cooldown can wait up to three seconds for the original permission; another menu, another press or respawn cancels that request. The OSS retail session confirmed the local PvE UI scope; it did not record the prompt stack at the instant of the death key.

If the player presses during the deployment cooldown, the same Leave Match prompt may remain open while the game finishes enabling role selection. The client preserves the original key press for up to three seconds. Another press, dismissal, a different prompt or respawn cancels that request. The dialog remains untouched until role selection is actually available.

The launcher supplies `-BrtLocalPveUi` for a local PvE session. The client also requires its own completed loopback travel command, the corresponding new world and server connection, the same local player, a running Easy, Normal or Hard PvE round, and the player's replicated Death status. The previous observation must show clear menu stacks. The new prompt must match the original type, owner, localized title, description and two options. A replaced dialog, open menu, different controller, respawn or loss of selection permission cancels the gesture.

For the split community source, apply `split.patch` and `sdk-split.patch`. Copy `DeathMenu.hpp` and `DeathMenu.sdk.hpp` beside `ProjectReboundMainDLL/Client/AutoConnect.cpp` before building. The patch calls the existing game-thread command pump.

For v0.8.4, apply `v084.patch` and `sdk-v084.patch`. Copy the same two headers plus `DeathMenuTravel.hpp` and `DeathMenu.v084.hpp` into `Payload/Utility`. The existing initial connection and reconnect branches publish the identity of their completed travel operation. The game's character UI tick checks the room's own local player, including when another character supplies the tick. Opening the selection screen requires at least one character tick after the original prompt closes. Both project patches add the original Blueprint's missing Back implementation to the build.

The verifier compiles the original and patched translation units against the full game SDK. It runs the calls extracted from each version against controlled input, localized text, game state and CommonUI widget stacks. It records each case and both source digests under the selected output directory. The recorded player session documents the original symptom. A fresh retail playthrough is still needed to verify the patched screen in the running game.
