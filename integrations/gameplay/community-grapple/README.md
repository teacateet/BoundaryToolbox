# 本机 PvE 钩索冷却

`live35` 的 OSS 普通房首次抓住锚点后，服务端在第 4 条命的 11,436 ms 恢复待命并结束冷却，到 47,312 ms 死亡前未再次锁定。本机同一条命收到了第 2 至第 6 次按键；每次本件钩索都仍是 `phase=0 cool=1 enabled=1 active=0`。角色的 `cooled=1` 不能代替装备自己的冷却位。客户端按键和专服采样使用不同的时钟；这两份记录本身不能说明哪一个原始网络通知被遗漏。

普通房现在用专服原生状态作为依据：同一条命、同一件钩索必须经历使用、待命冷却、冷却结束，才通过该装备的 `ClientEndHookLockCoolDown()` 给拥有者补发一次结束通知。SDK 将这条通知标为可靠客户端 RPC；装备上的 `bIsInCoolDown` 本身没有网络复制标记。没有确认拥有连接时暂缓；死亡、换装或新的发射过程会丢弃旧通知。这里只通知拥有客户端；输入、锁定、冷却计时和牵引均由游戏处理。

服务端 `Win64/logs/BRT-grapple-sync-<PID>.log` 分别记录 `owner-rpc-called`、`owner-route-missing`。前者只表示专服调用了可靠通知。是否恢复，要看 Steam 普通局同一命第二次手动按键后确实再次出绳、锁定并牵引。[冷却边沿回归](cooldown-delivery.test.cpp)

玩家报告同一条命只能牵引一次。社区专服在现有登录和游戏 Tick 观察当事玩家佩戴的钩索。每次状态变化记入本房间的 `logs/log-brt-*.txt`。同一玩家、生命和装备的记录能显示首次锁定、回收、原生冷却位起止和后续锁定。已安装版本的历史对局尚无第二次实际牵引的回执。

读一份房间日志即可按生命和装备查看时间。输出使用房内临时编号，时间从本条生命首次被观察到时起算。

```powershell
node integrations/gameplay/community-grapple/read-observations.cjs <一份房间日志>
```

| 字段 | 读取方式 |
| --- | --- |
| `owner/life/slot` | 在同一个房间进程内有效。重生、死亡计数变化、可控角色更换会分开记录。换下或更换钩索会另起装备编号。 |
| `hook` | 原生钩索状态。0 待命，1 发射中，2 已锁定，3 回收中。 |
| `cool` | 当前专服装备实例的原生冷却位。0、1 的变化记录发生时实际采到的值。 |
| `anchor` | 状态已锁定，且原生锁定数据包含有效锚点类型时为 1。日志不含坐标和目标身份。 |
| `permille` | 当前装备的 `GetCoolingDownPercent()` 读数乘以 1000。超出 0 至 1 或无效的读数记为 -1。 |
| `event` | `baseline` 表示开始观察，`change` 表示状态发生变化。从锁定或回收进入待命后，还会在游戏时间经过约 8 秒和 16 秒时取样。再次发射会结束此次定时取样。`slot-end/life-end` 记录上一次样本并关闭该段。`limit` 表示本条命已达到记录上限。 |

上线规则依赖首次选角的房主身份核验。登录业务取得已登记房间的房主回包后，检查专服权限和原生模式、地图组合。每次只从该本机单人房的当前控制器读取其占有且存活的角色，并检查钩索属于该角色的当前机动槽。每条命最多输出 193 行原生状态，含末尾的上限标记；独立的冷却通知记录每个房间进程最多 64 行。[读取和发送代码](Observer.hpp) · [采样和通知条件](Timeline.hpp)

相应社区源码先应用库存登录补丁，再应用本目录的发行版或主线差异。两份差异均包含新增头文件。工具箱正式房间日志已经接受本功能的固定格式。只有包含观察代码的社区专服发行件才会产生日志。[发行版差异](v084-community.patch) · [主线差异](main-community.patch) · [工具箱日志差异](toolbox-journal.patch)

两次新的锚点锁定应出现在同一 `owner/life/slot`，期间经历退出锁定。若角色换命、换槽或记录从锁定中途开始，读表器会分段。Tick 能漏掉同一帧内完成的转换。服务器看到第二次锁定后，仍需同一现场的玩家第二次手动输入及实际牵引位移才能确认玩法恢复。[验证记录](verification.json)
