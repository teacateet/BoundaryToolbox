# 工具箱公开房与十人联机

**使用：** 房主在「联机 → 房间」创建好友房，再点「公开我的房间」。其他 BRT 玩家打开同一页，在「工具箱公开房间」看房主的 Steam 昵称，点「加入房间」。选择公开之前不会登记。撤下房间会断开这间房的好友组网，已发出的邀请不再通往房主；继续邀请时重新生成链接。双方需要在线 Steam 和支持此功能的 BRT。

**目录 API 契约（v2）**：使用 Steam App ID `1364020` 和游戏自带 Steamworks v157。Steam 只负责查找房间；游戏流量继续走 BRT 的游戏 UDP 通道。社区固定服的 `GET /servers` 保持原有含义。v1 好友邀请没有房主指纹，不能用于 v2；双方须升级并重新复制邀请。

| Steam 大厅数据键 | 发布者写入 | 浏览者接受条件 |
| --- | --- | --- |
| `brt.directory` | `boundary.rooms.2` | 精确匹配；不混入原版大厅或其他协议版本 |
| `brt.host` | 当前 Steam 昵称 | 非空；去掉控制字符，最多 48 个字符。昵称用于显示，不是唯一标识 |
| `brt.invite` | `brt://room2/<32 位房间凭据>/<虚拟 IPv4:游戏端口>/<64 位房主证书 SHA-256>` | 成员凭据与房主密钥分开，房主私钥仅在内存中；不接受旧好友邀请、任意网址或裸地址 |
| `brt.seen` | Steam 服务器时钟的 Unix 秒数，每 10 秒更新 | 超过 45 秒或明显来自未来的记录不显示 |

房主先建私有大厅，写全字段后才设置为可搜索的 Invisible 类型；这种类型可以被工具箱按标记搜索，又不会作为原版大厅显示给 Steam 好友。查询采用全球范围；联机页每 20 秒刷新，可手动刷新。服务不可用显示错误，不伪装成“没有房间”。正常撤下时离开 Steam 大厅，房主进程退出时独立目录进程也会收到 EOF。房主昵称与加入链接只应在主动公开后进入目录，不登记 Steam 账号、内网物理地址或组网高级设置。见 [Steam 大厅 API](https://partner.steamgames.com/doc/api/ISteamMatchmaking)。

## 十人房该把专服放在哪里

**中继和授权：** 中继 TLS 默认验证系统信任链及服务名。自建中继可在房主和房客的启动环境中设置相同的 `BRT_ROOM_RELAY`（单个固定地址）和 `BRT_ROOM_RELAY_SHA256`（由管理员从服务端证书取得、经可信渠道发布的 64 位指纹）。不要从一次未验证的网络连接建立信任。内置中继在本轮检查时返回自签证书，未取得可信公开指纹；默认不能保证连上。高级手动组网也必须设置房间密码，不再开放通用虚拟网卡。

好友房 QUIC 双向验证：房客核对邀请中的房主证书指纹并验签；房主要求由当前房间凭据证明成员资格。这证明持有邀请，不代表识别每个真人。公开房的成员凭据对浏览者可见。高级手动组网使用共享密码验证成员，不提供好友邀请独有的房主身份绑定。撤权同步阻止旧代提交新的游戏 UDP 写入和回包；网络或系统已接收的数据不可追回。进程句柄与 UDP 所有权检查针对实际游戏端口；Windows 查询所有权与发送不是一个原子系统调用。

BRT 的「创建好友房」已经启动独立的 Windows 游戏专服。「进入房间」才启动本机玩家客户端。好友之间无需两两互发全部游戏数据；对局状态以专服为准。因此应先决定**哪台机器跑专服**，再决定玩家如何连过去。

| 方案 | 对开房玩家的影响 | 适合先试的情况 |
| --- | --- | --- |
| 房主电脑跑玩家和专服，好友直连或 VNT 中继 | 一台电脑承担客户端渲染、专服模拟和对所有玩家的上行 | 临时小房，不需要常驻设备 |
| 另一台家用 Windows 机器只开专服 | 玩家电脑释放专服负担；若仍在同一家庭网络，家庭总上行没有增加 | 怀疑 CPU、帧时间或客户端与专服互抢资源 |
| 社区节点或托管 Windows 专服 | 专服模拟和上行都移出玩家家庭。玩家作为客户端加入，节点由管理员维护 | 固定十人场次、玩家分属不同网络 |
| 仅增加 UDP 中继 | 改善部分 NAT 环境的可达性，专服仍在原主机，每份下行同步仍需从该机器发出 | 上不去房或直连路径差，但专服性能和上行已有余量 |

当前 BRT 可通过工具箱分享常驻机器上的好友房，或让玩家加入已有、可达的固定服游戏地址。当前没有替远端节点分配机器、按按钮远程开服的管理 API。不要把“能查到公开房”当成“有十个可用位置”或“已验证十人容量”。

**十人验收：** 先选相同地图和模式，分批加入 1、5、10 名真人；在出生、交战及 AI 活跃阶段对比专服最忙 CPU 核心、内存、每秒出站字节、玩家 RTT 和丢包，以及房主客户端帧时间。第二轮只把专服换到独立节点。若换到家中另一台机器后帧时间改善而远端玩家仍同时卡顿，下一轮测独立网络上行，不靠更换中继来推断容量。

参考：[Epic 的客户端与独立服务器模型](https://dev.epicgames.com/documentation/en-us/unreal-engine/networking-overview?application_version=4.27)、[Valve 的中继职责与接入条件](https://partner.steamgames.com/doc/features/multiplayer/steamdatagramrelay)。

## 本轮验证

在一台 Windows 机器上运行两个独立 Steam SDK 进程，用一次性筛选键和无实际专服的测试邀请，发布前查到 0 间，发布后另一进程查到 1 间并读回房主名和完整邀请，撤下后又查到 0 间。使用同一个 Steam 账号；不是跨账号、跨家庭或满员对局测试。可用 [目录回归脚本](../tools/test-steam-room-directory.ps1) 复验。

[安装回归脚本](../tools/test-obsolete-components.ps1) 用实际 19.20.41、19.20.42 玩家 ZIP 和 V0.3 启动包验证：新装时清理旧玩法 DLL 和旧批处理，保留自定义同名启动器；补入已知旧启动器后，二次安装仅清理该启动器，保留房间配置。第三次安装没有重复清理。
